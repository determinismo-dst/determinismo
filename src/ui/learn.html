How determinismo finds bugs

A run is many timelines of one system, each a different way the world could have gone: different faults, timings, loads and choices. Every timeline is deterministic, so any one of them can be replayed exactly, and opened at any moment. This page explains each technique a run uses, and then how they combine.

1. A deterministic machine

Foundations

The system under test runs in a virtual machine whose every input is controlled: a patched KVM with one virtual CPU, no hardware randomness, and a clock made of retired branches, the one count the hardware keeps deterministic. Given the same seed and inputs, the machine executes the same instructions in the same order, every time. Each node of the system (a container from Compose, a Kubernetes pod, or a program's own nodes) runs inside it.

Where you see it: every failing example can be replayed; a run's page says its seed and inputs; "Run again" starts a new seed.
Good forReproducing any failure exactly, however rare: a bug found once is found every time, and fixed against the same timeline.
PitfallsOne virtual CPU per machine: true multi-core effects (weak-memory reorderings) are not reproduced. Virtual time is not real performance. Anything outside the machine needs egress.
Learn more
  • Will Wilson, “Testing Distributed Systems w/ Deterministic Simulation” (Strange Loop 2014, video)
  • Antithesis, “So you think you want to write a deterministic hypervisor?”
  • FoundationDB, “Simulation and Testing”

2. Timelines, moments and replay

Foundations

A timeline is one execution of the machine from a starting point. A moment is a point on it, named by its virtual time. Each timeline keeps a tape: every choice made along it (each random draw, each fault, each answer from outside). Replaying the tape reproduces the timeline exactly, and stopping the replay at a moment gives a machine you can look into: run a command, take a file out, read every thread's stack, or open a REPL there.

Where you see it: a property's examples ("Causality", "Shrink", "Export"), the Logs explorer, determinismo replay --until …, the Notebook's actions.
Good forLooking at a failure from inside: the exact state just before it, as many times as needed.
PitfallsA tape belongs to one build and its inputs: change the system and old tapes are refused. Late moments of long timelines take a while to reach (snapshots help).
Learn more
  • O’Callahan et al., “Engineering Record and Replay for Deployability” (USENIX ATC 2017)
  • rr: lightweight recording & deterministic debugging

3. The multiverse tree

Foundations

Instead of many independent runs from the start, determinismo explores a tree. Timelines run in generations; one that reached a behavior no timeline had reached is returned to just after it (from a snapshot there) and branched with new seeds, so the next timelines start from the interesting state instead of rediscovering it. A sometimes or reachable assertion made true, or a node printing something that reads as trouble, is returned to first. Every timeline's path is kept, so it replays alone.

Where you see it: the Logs explorer's map (one path per timeline), a timeline's "why" (the reason its branch point was chosen), the Utilization's discovery curve.
Good forDeep states: a bug that needs a leader change, then a crash, then a partition is reached by building on timelines that already got partway.
PitfallsIt follows novelty, and novelty can be noise: on 2026-11-11 random ids in Kafka's logs made 74% of output kinds look new, until the templates blanked them. States the tree has seen many times get fewer new timelines, even if a bug is one step away.
Learn more
  • Ecoffet et al., “Go-Explore: a New Approach for Hard-Exploration Problems” (2019)
  • Ecoffet et al., “First return, then explore” (Nature, 2021)

4. Randomness and named decisions

Making timelines differ

Everything random inside the machine comes from the platform: the kernel is reseeded per branch, and the SDKs' random calls draw from the same source. A draw can carry a name (decide, random_below_named), which makes it a named decision: the report counts what timelines drew for it, and a strategy can steer it. buggify(name) makes rare paths common: a code path that runs only on a rare condition runs whenever the draw says so.

Where you see it: the run report's "Named decisions" (what the timelines drew, by name), a timeline's tape.
Good forMaking rare paths common (buggify), and seeing what timelines chose (named decisions).
PitfallsA program that seeds its own generator from a constant explores nothing: draw from the SDK or the platform. Too many buggified paths at once and the system never does anything normal.
Learn more
  • FoundationDB, “Simulation and Testing”

5. Swarm testing

Making timelines differ

Running every feature in every timeline hides bugs that need some features off: a fault that keeps resetting a cluster also keeps it from reaching the state where a bug lives. So each timeline draws its own configuration (swarm testing, Groce et al. 2012):

  • Drivers: which of a scenario's workload drivers run (at least one), and the load's shape in stretches (steady, quiet, a spike).
  • Fault kinds: each kept with a drawn probability (a "meta-swarm": how many kinds are kept is itself drawn), each weighted 1 to 64.
  • Fault regimes: a rate (a mean gap of 100 ms to 25.6 s) and a duration scale (1 to 8), lasting 10 to 120 s, then redrawn with the kinds and weights.
  • A workload's own choices: swarm_choice in every SDK, and knobs a node draws (a timeout, a buffer size).
  • Guidance itself: which share of learned ranges a timeline keeps (below).
Where you see it: fault_swarm and fault_regime events, a property example's knobs, "Triggers and suppressors". --no-swarm runs the fixed injector, for comparisons.
Good forBugs that some features hide: a fault that keeps resetting a cluster also keeps it from reaching the state where the bug lives.
PitfallsA bug that needs several features on at once is rarer (each one is off in some timelines): more timelines are needed. Which feature mattered is not obvious without triggers and suppressors.
Learn more
  • Groce, Zhang, Eide, Chen, Regehr, “Swarm Testing” (ISSTA 2012)
  • Groce et al., “Help, help, I’m being suppressed! The significance of suppressors in software testing” (ISSRE 2013)

6. Faults

Making timelines differ

The fault injector acts inside the machine, so faults are part of the timeline: replayed with it, and explained by its events. A system's description says which kinds each node allows.

Network

Partitions into 2–3 groups (stopped, slowed or jammed; both ways or one way), a node's inbound or outbound clogged, a baseline of delay, jitter and drops per timeline.

Nodes

Kill and restart, stop (SIGTERM, then a kill), pause, throttle, a process killed; several nodes at once, capped by a scenario's nodes_down_max.

Power and disks

A power loss keeps only what was synced (crash); half of them persist part of what was not, as a host's flusher may have (partial persistence); outage takes several nodes at once; wipe starts fresh.

Disk I/O

The disk through device-mapper: every I/O failing, writes failing, or writes acknowledged and never stored. Durability points hold a node's fsyncs while a fault lasts (sync_stall).

Time

Clock skips forward or back (a quarter permanent), one node's realtime clock skewed (sometimes strobing), and CPU modulation: stretches running up to twice as slow.

Concurrency

Thread pausing at instrumented points, the guest scheduler's choices drawn (interleave), crash points at a JVM node's state transitions.

Processes

Signals a process catches, and errors a system call may return, made common for code you cannot edit.

Aimed and custom

fault_aim sends half the faults at the node that matters (the leader, the primary, a coordinator); custom faults run your commands at random times; quiet periods hold faults off.

Where you see it: fault events in the Logs explorer, "During faults" on a property's page, --faults +crash,-partition to choose kinds.
Good forCrash recovery, partitions, lost or unsynced writes, failing disks, clock trouble: what distributed systems get wrong most.
PitfallsToo many faults keep a system in recovery forever (hence regimes and quiet stretches). A fault the real world cannot produce makes false findings: a power loss's model is checked against stock ext4 before a finding is claimed. Some failures are allowed by the system's own guarantees: read its documentation first.
Learn more
  • Bailis & Kingsbury, “The Network is Reliable” (ACM Queue, 2014)
  • Alquraan et al., “An Analysis of Network-Partitioning Failures in Cloud Systems” (OSDI 2018)
  • Pillai et al., “All File Systems Are Not Created Equal” (OSDI 2014)
  • Ganesan et al., “Redundancy Does Not Imply Fault Tolerance” (FAST 2017)
  • Dan Luu, “Files are hard”
  • Justin Sheehy, “There is No Now” (ACM Queue, 2015)
  • Yuan et al., “Simple Testing Can Prevent Most Critical Failures” (OSDI 2014)

7. Timing faults

Making timelines differ

Some bugs need no failure at all, only an unlucky order of events. Three techniques change timing without breaking anything:

  • Thread pausing: instrumentation callbacks (a line, an edge, a branch) are pause points. In one stretch of two seconds in four, one point in 64 becomes slow: every thread reaching it waits 1–10 ms, so a check-then-act's checks run before any of its acts.
  • Interleaving: for a while, some of the scheduler's choices among a node's threads are drawn: a woken thread runs first, a tick preempts, a random runnable thread runs next.
  • Process pauses and CPU modulation: a node stops for a while; stretches of execution run slower, so interrupts land elsewhere.

These are what CI jobs use by default (faults: "timing"): a test suite's tests, unchanged, under schedules they never see on a laptop.

Good forRaces, check-then-act bugs, flaky tests: bugs that need only an unlucky schedule.
PitfallsPause points come from instrumentation: uninstrumented code is disturbed only by the scheduler and process pauses. A pause can trip a timeout the code is right to enforce: a timing-sensitive test failing under pauses may be the test's assumption, not a bug.
Learn more
  • Burckhardt et al., “A Randomized Scheduler with Probabilistic Guarantees of Finding Bugs” (ASPLOS 2010)
  • Lu et al., “Learning from Mistakes: A Comprehensive Study on Real World Concurrency Bug Characteristics” (ASPLOS 2008)

8. The machine's boundary: egress and ingress

Making timelines differ

A deterministic machine has no network beyond itself. Egress lets a node reach an allowed outside server (a model's API, an external service): the explorer makes the real connection on the live timeline, and every answer goes on the tape, so a replay answers the same with nobody called. Connections can fail at the boundary (refused, reset, slow), drawn per timeline. Ingress is its inverse: a browser or curl reaches a node's port through the live timeline's listener, each connection's bytes recorded, so a replay delivers them again with nobody outside. While it listens, the timeline runs no faster than the wall clock.

Good forTesting a system that calls real services (a model, an API), or one driven from a browser, while keeping exact replay.
PitfallsLive calls cost money and hit rate limits. A replay only answers what was recorded: an explored future that asks something new gets a reset. Plain-HTTP traffic is recorded as is (TLS stays encrypted on the tape).
Learn more
  • O’Callahan et al., “Engineering Record and Replay for Deployability” (USENIX ATC 2017)
  • Hermit (Meta): deterministic execution of Linux programs

9. Behaviors and novelty

Guidance

The tree needs to know what is new. A behavior is anything categorical a timeline showed: an assertion's outcome, an event with its kind and node, a line or edge of code coverage, and a kind of output line (its numbers, hex and random ids blanked, so "took 12 ms" and "took 40 ms" are one kind). A timeline that shows a behavior no timeline showed before is where the tree returns.

Where you see it: the Utilization's discovery curve; coverage comes from the language's instrumentation (C, Zig, Rust, Go, Python, the JVM, Node.js, .NET), automatic for the JVM.
Good forNoticing that a timeline did something new, with no assertion written for it: new code, new events, new kinds of log line.
PitfallsCoarse: a new line of code is new once, however differently it is reached later. Noisy logs fake novelty. Each timeline keeps at most 8,192 behaviors: a timeline full of noise drops what comes late.
Learn more
  • Michał Zalewski, AFL’s technical whitepaper
  • Zeller et al., “The Fuzzing Book”

10. Sought and severe states

Guidance

Some novelty matters more. A sometimes or reachable assertion made true is a state the programmer marked as worth reaching; a node printing an error, an exception or a timeout is a state the system itself marks as unusual. The tree returns to these first, so the next timelines start where things are already going wrong.

Good forSpending timelines where the programmer or the system says things get interesting.
PitfallsRoutine warnings (a retry, a reconnect) read as trouble too, and pull the tree there.
Learn more
  • Antithesis docs, “Asserting correctness”

11. Guidance assertions and optimization

Guidance

A guidance assertion (alwaysGreaterThan, sometimesLessThan, …) says how far a timeline is from a boundary: a timeline that came closer than any before is new. An optimization (sdk.optimize) keeps, per bucket, the timeline with the best score (the longest queue, the slowest request), and branches from it: each bucket climbs on its own.

Good forDriving toward boundaries and extremes: the fullest queue, the slowest request, the value closest to a limit.
PitfallsSomeone has to write the metric. Climbing one score finds its local best, not necessarily the bug.
Learn more
  • Mouret & Clune, “Illuminating search spaces by mapping elites” (2015)

12. Learned ranges

Guidance

Without anyone writing an assertion, the explorer learns each workload event's numeric fields' ranges: for every (event, field), the highest and the lowest value seen. A timeline that goes past either end has done something unusual, and is returned to (likely invariants, Fioraldi et al. 2021). Identifiers and clocks are left out, and each timeline keeps only a drawn share of the fields (none, a quarter, half, three quarters or all), so ranges never crowd out other guidance.

Where you see it: the report's collapsed "Learned ranges" appendix; --no-ranges to compare.
Good forUnusual numbers with nobody writing an assertion: a record retry count, a queue deeper than ever.
PitfallsCounters that only grow always set new records (identifiers and clocks are left out by name, not every such field). Many ranges dilute other guidance, hence each timeline keeps a drawn share. Useless when a workload reports no numbers.
Learn more
  • Fioraldi et al., “The Use of Likely Invariants as Feedback for Fuzzers” (USENIX Security 2021)
  • The Daikon dynamic invariant detector

13. Strategies and the bandit

Guidance

Where to branch and what to draw can be decided by a strategy: a program speaking a JSON protocol, in any language (random, mutation from coverage, extremes, an LLM). The built-in explorer is the default. A bandit learns which settings pay off (which fault rates found new behaviors) and draws them more often, while still exploring the others.

Good forAdapting a run to what pays: fault rates that found new behaviors are drawn more.
PitfallsRewards change as a run goes (what was new becomes known), which bandits assume they do not. Smarter is not always better: in our 2026-11-07 comparisons no LLM or council strategy beat the built-in explorer.
Learn more
  • Sutton & Barto, “Reinforcement Learning: An Introduction” (chapter 2: multi-armed bandits)
  • Yue et al., “EcoFuzz” (USENIX Security 2020): fuzzing as a multi-armed bandit

14. Targeted runs

Guidance

--changed <diff or git range> aims a run at a change: its hunks are matched to line coverage, the tree returns first to timelines that ran changed code, and the report says which hunks ran in how many timelines, and which never ran.

Good forA pull request's change: did the timelines run it, and does it break under faults?
PitfallsOnly code the instrumentation reports as lines can match a diff. The tree returns to timelines that ran changed code; it does not steer toward changed code no timeline reached yet.
Learn more
  • Böhme et al., “Directed Greybox Fuzzing” (CCS 2017)

15. Assertions

Judging

Properties are what a run judges. Each SDK (Zig, C/C++, Rust, Go, Python, the JVM, Clojure, JavaScript, .NET) has the same kinds:

KindPasses whenExample
alwaystrue every time it is evaluated, in every timelinethe balance is conserved
always_or_unreachabletrue whenever reached; never reaching it is finea recovered log is contiguous
sometimestrue in at least one timelinea transaction was aborted
reachablereached in at least one timelinethe leader stepped down
unreachablenever reachedtwo leaders in one term

Assertions are declared as code loads, so one never reached still shows: sometimes and reachable ones that never came true fail, which says a run did not explore enough.

Good forSaying what must hold (always), and what must be possible (sometimes): the second also proves a run explored enough.
PitfallsAn assertion stricter than the system's real guarantee fails for nothing. A sometimes never made true fails the run: a workload that never reaches it reads as a failure of exploration, which it is.
Learn more
  • Antithesis docs, “Asserting correctness”
  • Claessen & Hughes, “QuickCheck” (ICFP 2000)
  • Hypothesis (property-based testing for Python)

16. Default properties

Judging

Every run also judges what any system should do: no process crashes (signals from the kernel's log, core dumps kept), no unexpected container exits, test commands exit with zero, peak memory under 95%, logging under 200 MB an hour of virtual time, and a language's own failures (Go and Rust panics, data races, Java's uncaught exceptions). A node's known failure texts or exits can be declared, so they are counted rather than failing.

Good forCatching crashes, exits and runaway memory or logs with nothing written.
PitfallsA system that exits or crashes by design needs its known exits and texts declared, or every timeline fails.
Learn more
  • Yuan et al., “Simple Testing Can Prevent Most Critical Failures” (OSDI 2014)

17. History checkers

Judging

Some guarantees are about whole histories, not single moments: is this history of reads and writes serializable? Workloads record their operations, and Elle checks them against the consistency the system claims (serializable, snapshot isolation, linearizable…), naming the anomaly it found (G1a, G2, lost update) and the operations in it.

Good forIsolation and consistency anomalies (lost updates, G1a, G2) found from histories of reads and writes.
PitfallsThe workload must record its operations, and be checked against what the system itself claims: a weaker claim allows more. Operations whose outcome is unknown (a timeout) weaken what can be concluded.
Learn more
  • Kingsbury & Alvaro, “Elle: Inferring Isolation Anomalies from Experimental Observations” (VLDB 2020)
  • Jepsen’s analyses

18. Tests as properties (CI)

Judging

determinismo-ci runs a repository's own test suite inside timelines. Each test is a property (test passes: <class>::<name>); a job is one run, its shards spread across timelines, under timing faults. A test failing in every timeline fails; one failing in some is flaky, and each flaky failure can be replayed exactly. The CI page shows each repository's jobs and every test that did not pass everywhere.

Good forA suite people already have: its flaky tests found, each failure replayable at its moment.
PitfallsTests that assume timing (a sleep, a short timeout) flake under timing faults by design: the failure may be the test's. A test touching the network outside the machine needs egress.
Learn more
  • Luo et al., “An Empirical Analysis of Flaky Tests” (FSE 2014)
  • Google Testing Blog, “Flaky Tests at Google and How We Mitigate Them” (2016)

19. Triggers and suppressors

Understanding a failure

Because each timeline drew its own configuration, failures can be compared with what was drawn: a trigger is a feature clearly more common among failing timelines than overall, a suppressor one clearly rarer (95% intervals, widened for how many features were tested). Fault regimes count by time: a failure counts for the regime active at its moment.

Good forWhich drawn feature a failure needs, or cannot happen with.
PitfallsCorrelation, not causation: confirm with a replay or a counterfactual. Fewer than five failures give no verdicts.
Learn more
  • Groce et al., “Help, help, I’m being suppressed! The significance of suppressors in software testing” (ISSRE 2013)
  • Liblit et al., “Scalable Statistical Bug Isolation” (PLDI 2005)

20. Causality

Understanding a failure

From moments before a failure, many futures are explored: how likely is the bug from each moment? The probability jumps where the bug was decided, and the events just before the jump are the cause. Shrink then removes what the failure does not need (faults, operations) while it still fails.

Good forWhere a failure was decided, and the smallest version of it.
PitfallsCostly: many futures from each moment. Probabilities from few futures are rough.
Learn more
  • Zeller & Hildebrandt, “Simplifying and Isolating Failure-Inducing Input” (TSE 2002)

21. Debugging at a moment

Understanding a failure

Run a command

In any node at a moment (--exec), the system held while it runs or running on.

Files and stacks

Take a node's file out exactly as it was; every thread's stack; a profile of where time went.

A REPL in the timeline

nREPL into a node at a moment; each message a recorded step, the session replayable.

Counterfactuals

Change something at a moment (a file, a config) and explore its futures: does the bug still happen?

Retroactive logging

Verbose output turned on after the fact: the replay regenerates it.

Queries and the Notebook

Every timeline's events in a database: searches, event sets, SQL, and Clojure cells.

Good forAnswering why with the machine itself, not guesses from logs.
PitfallsA command at a moment can change what happens next: compare with the untouched timeline before concluding.
Learn more
  • O’Callahan et al., “Engineering Record and Replay for Deployability” (USENIX ATC 2017)
  • rr: lightweight recording & deterministic debugging

22. Findings over runs

Understanding a failure

A run is compared with the previous run of the same system and scenario: each property new, ongoing, resolved or rare, with its history. What-if runs can stay out of that history.

Good forKnowing whether a property is new, still failing, or fixed.
Pitfalls“Resolved” can mean the new run never reached the state: check that its timelines got there.

23. How they combine

How they combine

No technique finds much alone. A bug needs a state (reached by the tree), a disturbance at the right time (faults, timing, swarm), something that notices (a property), and a way to understand it (replay, causality, triggers). These combinations found real bugs.

Power loss × partial persistence × the tree × recovery checks

crashpartial persistencedurability pointstree returning to new statesdefault: no unexpected exits

A node writes a file it never syncs, then a power loss keeps part of it. The node never starts again. A node's identity key, a server's epoch files, a database's version file, a keystore and others were found this way: the tree returns to a timeline where the node had just written the file, partial persistence decides how much of it survives, and the restart's failure is a default property. The replay shows the file's bytes at the moment of the power loss.

Swarm × faults aimed at a coordinator × history checkers

fault_aimswarm regimesEllecausality

Workloads aim faults at the node that matters: the transaction coordinator, the leader. With fault regimes drawn per timeline, some timelines move leadership in a quiet stretch, others during load, and checkers judge the histories that result. Bugs of this shape, ownership moving at the wrong moment: a group coordinator activated by its own stale load, and a slot migration cancelled after handover (a stale owner winning, acknowledged writes deleted).

Clock skew × version ordering × read-after-write

clock skewswarmproperties on reads

One node's clock runs seconds ahead while others write. Two object stores ordered object versions by the clock of whichever node coordinated: a later acknowledged version was never the latest. Skew is off in some timelines, so triggers compare timelines with and without it.

Thread pausing × coverage × the tree

instrumentationthread pausinginterleavebehaviors

The same instrumentation does two jobs: its lines are behaviors the tree seeks, and its callbacks are where threads pause. A check-then-act race needs both threads at the check before either acts; pausing at a slow point lines them up, and coverage tells the tree when a new interleaving reached new code. A database's change stream reporting after a later head was found with thread pausing; the 64-thread transfer race in examples/race shows the mechanism.

A test suite × timing faults × timelines (CI)

determinismo-citests as propertiesthread pausingreplay

Clojure's own test suite, unchanged: 251 tests across 12 timelines under timing faults. The add-watch test failed in some timelines only: its watch also fired for the test's own latch, a race in the test. Each flaky failure opened at its moment, with the exact schedule that made it fail.

Egress or ingress × tapes × replay

egressingresstapesREPL sessions

An agent in a node calls a model's API, or a person drives a node's web UI from a browser. The live timeline talks to the outside; the tape keeps every byte. A replay has no side effects and needs nobody outside, so a crash during that session is as debuggable as any other.

Learned ranges × swarm × the tree

learned rangesswarmed sharebehaviors

A workload reports its numbers (operations, slowest latency, queue depth); the explorer keeps their extremes. A timeline with a record-long retry loop is returned to, even though no assertion mentions retries. Which share of ranges each timeline keeps is drawn, so ranges help without drowning coverage and assertions.
